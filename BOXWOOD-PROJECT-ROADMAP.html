3. Work still required before launch

Priority 1 Hosting and operations

  • Host frontend over HTTPS.
  • Host API separately or in the same deployment.
  • Use managed PostgreSQL or hosted SQLite-compatible storage for production.
  • Set backups, logs, uptime monitoring and a real domain.

Priority 2 Booking workflow

  • Add staff-only enquiry dashboard.
  • Send email notifications to Boxwood.
  • Track enquiry status: new, contacted, confirmed, cancelled.
  • Connect real game dates, room inventory and ticket availability.

Priority 3 Commercial flow

  • Confirm package tiers and pricing.
  • Add guest count, stay date and room preference fields.
  • Add payment or deposit provider only after availability is confirmed.
  • Add terms, cancellation policy and privacy notice.

Priority 4 Quality and accessibility

  • Add automated API and browser tests.
  • Test keyboard navigation, focus states and screen readers.
  • Compress and serve responsive image sizes.
  • Measure conversion, performance and form completion.

4. Hosting options

Simple recommended setup

Frontend: Netlify, Cloudflare Pages or GitHub Pages.

API: Render, Railway, Fly.io or an Azure App Service running ASP.NET Core.

Database: Managed PostgreSQL for production. Keep SQLite for local development only.

This split keeps deployment simple and lets the static site stay fast while the API handles enquiries.

Single-provider option

Deploy the frontend and API to Azure App Service, with Azure Database for PostgreSQL and Application Insights.

This is more operationally coherent but usually costs more and needs more setup than the separate static-site/API approach.

Not yet hosted: The current GitHub Pages workflow is suitable for the static frontend, but it cannot run the C# API or persist production enquiries by itself.

5. Current security exposure

The current build is an MVP and should not be treated as a production booking system yet.

HIGH
Open CORS policy. The API currently allows requests from any origin. Restrict this to the real website domain before hosting.
HIGH
No staff authentication or authorisation. There is no protected admin area, so anyone who can reach a future admin endpoint could access data unless this is added.
MEDIUM
In-memory rate limiting. It resets when the process restarts and does not coordinate across multiple servers. Use platform or distributed rate limiting in production.
MEDIUM
SQLite operational risk. A local file is not ideal for concurrent production traffic, backups or multi-instance hosting.
MEDIUM
Forwarded IP trust. The API reads X-Forwarded-For; configure trusted proxy handling so clients cannot spoof the rate-limit identity.
LOW
Privacy and retention are undefined. Add a privacy notice, retention period, access controls, deletion process and encrypted production storage.
Already improved: SQL parameters are used, server-side input validation exists, no secrets are hardcoded, and the database file is ignored by Git.

6. UI design and image direction

UI additions

  • Real game-date cards with opponent, tip-off and availability.
  • Package tier comparison: Essential, Premium and Fireside.
  • Guest count, date and room preference fields.
  • Sticky mobile enquiry CTA.
  • Confirmation screen with next steps and contact details.
  • Accessible error, loading and success states.

More unique Islington look

  • Replace generic stock fireplace imagery with approved Islington photography.
  • Add a visual “house tour”: arrival, room, Emerald Lounge, fireplace and morning light.
  • Use close crops of timber, books, glassware, linen and heritage details.
  • Pair warm interior images with one Hobart/Mount Wellington context image.
  • Use consistent warm film treatment rather than unrelated stock photography.
Current image situation: The page currently uses an external Islington logo and one Unsplash fireplace image. The next design pass should replace these with licensed, brand-approved Islington assets and responsive local copies for reliability and performance.

7. Recommended delivery sequence

  1. Connect real data: game schedule, ticket allocation, package inventory and enquiry statuses.
  2. Harden the API: HTTPS, restricted CORS, production database, distributed rate limiting, authentication and logging.
  3. Deploy a staging environment: test frontend and API together with non-production data.
  4. Refresh the visual system: approved Islington photography, package tiers, dates and conversion-focused CTA.
  5. Launch carefully: privacy terms, monitoring, backups, staff process and a tested enquiry-to-booking handoff.
